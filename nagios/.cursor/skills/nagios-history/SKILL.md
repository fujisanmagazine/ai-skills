# Nagios 履歴分析

指定期間のアラート履歴を分析し、頻出アラート、フラッピング、通知負荷、悪化傾向を検出する。

## 引数

- `hours` (任意, デフォルト: 24): 遡る時間数
- `host_name` (任意): 特定ホストに絞る場合

## 手順

### Step 1: データ収集（並列実行）

まず集計済みツールを優先する。

1. **`get_alert_statistics`** (`hours_back={{hours}}`, `hosts=[{{host_name}}]` を必要に応じて指定) — 頻度、状態変化、自己回復率、傾向
2. **`get_notification_analysis`** (`hours_back={{hours}}`, `hosts=[{{host_name}}]` を必要に応じて指定) — 通知負荷、ノイズ候補
3. **`get_flapping_report`** (`hours_back=min({{hours}}, 24)`, `hosts=[{{host_name}}]` を必要に応じて指定) — フラッピング候補

`get_alert_statistics` の結果が空、または詳細時系列が必要な場合のみ raw 履歴を追加取得する。

### Step 2: 補足データ（必要に応じて）

アラート件数が多い場合、上位のホスト/サービスについて以下を追加する。

4. **`get_alert_history`** (`hours_back={{hours}}`, `host_name=上位ホスト`) — 詳細な時系列
5. **`get_notification_history`** (`hours_back={{hours}}`, `host_name=上位ホスト`) — 通知詳細
6. **`get_service_availability`** (`hours_back=max({{hours}}, 24)`, `hosts=[上位ホスト]`) — ダウン時間、MTTR、SLO逸脱
7. **`get_coverage_gaps`** (`hosts=[上位ホスト]`) — 閾値不足や監視漏れの確認

### Step 3: AI分析

#### 分析の観点

1. **頻出アラートTOP10**: 同一ホスト/サービスのアラート回数でランキング
2. **フラッピング検出**: `get_flapping_report` の上位対象を優先し、必要なら raw 履歴で裏取り
3. **時間帯パターン**: 特定時間帯に集中するアラート（cronジョブ起因、バッチ処理起因等）
4. **相関分析**: 同時刻に発生するアラートのグルーピング（共通原因の示唆）
5. **通知負荷**: 通知件数の多い連絡先（アラート疲れのリスク）
6. **悪化傾向**: 直近で頻度が増加しているアラート
7. **慢性化候補**: 自動回復率が低く、長時間継続または通知が多い対象

#### 優先ルール

- 集計済みデータがあるときは `get_alert_statistics` / `get_flapping_report` / `get_notification_analysis` を優先する
- raw データは「集計結果の理由説明」か「個別イベントの時系列確認」が必要な場合だけ使う
- host 指定がある場合は `hosts=[host_name]` で必ず絞る

#### 出力フォーマット

```
## Nagios 履歴分析レポート（直近 {{hours}} 時間）

### サマリ
- 総アラート件数: N件
- 影響ホスト数: N台
- 影響サービス数: N件

### 頻出アラート TOP10
| # | ホスト/サービス | 回数 | 最終状態 | パターン |
|---|----------------|------|---------|---------|

### フラッピング疑い
- [ホスト/サービス] — N回の状態変化（直近M時間）

### 時間帯パターン
- HH:00-HH:00 に集中: [アラート一覧]（推定原因: cron/バッチ等）

### 相関グループ
- グループ1: [ホストA, ホストB, サービスC] — 同時発生N回（共通原因の可能性）

### 通知負荷
- [連絡先名]: N件の通知

### 推奨アクション
1. フラッピング対象の閾値見直し
2. ...
```
